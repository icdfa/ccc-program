## Part 1: Fundamentals of Security Auditing & PCI DSS

Before beginning the audit simulation, it is crucial to understand the framework you are auditing against and the responsibilities of a security auditor.

### 1.1 What is PCI DSS?
The Payment Card Industry Data Security Standard (PCI DSS) is an information security standard for organizations that handle branded credit cards from the major card schemes. The PCI Standard is mandated by the card brands but administered by the Payment Card Industry Security Standards Council. The standard was created to increase controls around cardholder data to reduce credit card fraud.

PCI DSS comprises 12 core requirements organized into six logical groups:
1. **Build and Maintain a Secure Network and Systems** (Req 1-2)
2. **Protect Cardholder Data** (Req 3-4)
3. **Maintain a Vulnerability Management Program** (Req 5-6)
4. **Implement Strong Access Control Measures** (Req 7-9)
5. **Regularly Monitor and Test Networks** (Req 10-11)
6. **Maintain an Information Security Policy** (Req 12)

### 1.2 The Role of the Auditor
As a cybersecurity consultant and auditor, your role is not to fix the systems, but to **assess, document, and recommend**. You must:
*   **Evaluate Evidence:** Review configurations, policies, and logs objectively.
*   **Identify Gaps:** Determine where the current state falls short of the required standard.
*   **Assess Risk:** Explain *why* a gap is dangerous (e.g., "Plain text storage allows attackers to easily steal card numbers if the database is compromised").
*   **Provide Actionable Recommendations:** Tell the client exactly what they need to do to achieve compliance.

## Part 3: The Comprehensive Audit Checklist

You will evaluate E-Shop against eight specific PCI DSS requirements. Review the expected controls for each requirement below.

| Req # | PCI DSS Requirement Description | Expected Control for Compliance |
| :--- | :--- | :--- |
| **1.1.4** | Install and maintain a firewall configuration to protect cardholder data. Requirements for a firewall at each internet connection and between any demilitarized zone (DMZ) and the internal network zone. | Evidence of a configured firewall restricting direct inbound traffic from the internet to the internal CDE. Traffic must be strictly limited to necessary ports/protocols. |
| **2.1** | Always change vendor-supplied defaults for system passwords and other security parameters before installing a system on the network. | Policies and technical evidence showing default passwords are changed and secure configurations are applied before systems go live. |
| **3.4** | Render PAN (Primary Account Number) unreadable anywhere it is stored (including on portable digital media, backup media, and in logs). | Evidence of strong cryptography (e.g., AES-256), truncation, or one-way hashing for stored credit card numbers in the database and backups. |
| **4.1** | Use strong cryptography and security protocols to safeguard sensitive cardholder data during transmission over open, public networks. | Evidence that only secure protocols (e.g., TLS 1.2 or higher) are used for data transmission. Deprecated protocols (SSL, TLS 1.0/1.1) must be disabled. |
| **6.4** | Follow change control processes and procedures for all changes to system components. | Evidence of a documented change management process, including approvals and testing before deployment to production. |
| **8.2.1** | Using strong cryptography, render all authentication credentials (such as passwords/phrases) unreadable during transmission and storage on all system components. | Evidence that passwords are not stored in clear text and are hashed using strong algorithms (e.g., bcrypt, PBKDF2) with a salt. |
| **8.3** | Secure all individual non-console administrative access and all remote access to the CDE using multi-factor authentication (MFA). | Evidence of MFA implementation for all administrative access to CDE servers, regardless of origin. |
| **11.2.2** | Perform quarterly external vulnerability scans via an Approved Scanning Vendor (ASV). | Recent external vulnerability scan reports showing scans are performed quarterly and have no vulnerabilities scored 4.0 or higher on the CVSS. |
